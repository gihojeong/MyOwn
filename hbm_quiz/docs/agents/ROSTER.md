### WARP 분할 제안 (권장)
- WARP 763 문항은 성격이 다른 두 덩어리다: **warpage·기계 응력**(f_warp·f_bond·f_sip 그림, 약 280) 과 **열 설계**(f_therm 477 + 열 키워드, 약 480). 필요한 전문성이 다르고 가족 초과 211 중 대부분이 열 계산이다.
- 방식: EA 가 W0.5 에서 열 문항을 `data/13_THERM.json`(code `THERM`, domain "열 설계와 방열")으로 **id 를 유지한 채** 옮기고 파일에 `"legacy_prefix": ["WARP"]` 를 둔다(검사기 지원 완료). 새 열 문항은 `THERM-LV-9xxx`. 05 의 domain 이름은 "Warpage 와 기계적 응력" 으로 바꾼다.
- 영향: 화면의 분야가 14 개가 된다 → **DA 확인 필요**(`EA_to_DA.md` §7). 승인되지 않으면 WARP 에이전트 1명이 전체를 맡되 작업 시간 1.5 배를 배정하고, 열 계산 가족 정리를 NUM 결과에 크게 의존한다.

### 병합은 제안하지 않음
- SAW(180)·FEOL(183)·MIX(217)는 작지만 성격이 독립적이고 보강 대상이므로 병합하지 않는다. 대신 신규 목표를 크게 잡았다.

## 4. 분야 에이전트 작업 규칙

1. **자기 data 파일만 수정**한다. 다른 파일(template.html, tools/, 다른 분야 data, _meta.json)은 건드리지 않는다. git commit 금지.
2. **id 유지**. 새 문항 id 는 `CODE-LV-9xxx`(9001 부터 순번). 난이도 변경으로 LV 가 바뀌면 새 id + `"prev"` 필드.
3. **삭제는 사유 기록**: 보고서의 삭제 표에 id · 사유(가족 초과 / 근중복: 대상 id / 사실 오류 복구 불가 / 타 분야 중복 / 품질 미달 재작성 불가).
4. 타 분야 문항: 고쳐서 `"mv": "CODE"` 로 이관 제안하거나 자기 분야 관점으로 재작성. 직접 다른 파일로 옮기지 않는다.
5. 작업 순서는 브리프 §4. **정답·사실 오류 → 가족·중복 정리 → ctx 정리 → 해설 → 제목·지표·그림 → 난이도 → 신규**.
6. 매 저장 후 JSON 유효성 확인(`python3 -c "import json;json.load(open('data/NN_CODE.json'))"`). 파일 구조(`domain`, `code`, `questions`)와 필드 순서를 유지한다.
7. **완료 게이트**: `python3 tools/validate.py --domain CODE --gate` 통과(차단 E 0, `E_JOSA_CIRC` 는 EA Phase 2 처리라 제외) → `python3 tools/build.py` → `node tools/smoke.js dist/HBM_quiz.html` 에서 figErr·errs 가 빈 배열.
8. 남기는 W 는 고치거나 문항에 `"vx": ["W_…"]` + 보고서에 사유. 면제 가능한 E 는 `WAIVABLE_E`(검사기 상단) 뿐이며 사유 필수.
9. 수치는 STANDARDS 2.2–2.4 범위 밖이면 출처(`src`)나 "가정" 명시가 필요하다. 업체 소문·추정을 정답 근거로 쓰지 않는다.
10. 정답 위치는 신경 쓰지 않는다(EA Phase 2). 단 보기 안에서 다른 보기를 번호로 가리키지 않는다.

## 5. 동시 작업 충돌 방지
- 파일 소유가 겹치지 않으므로 분야 에이전트는 완전 병렬로 일한다. `tools/validate.py`, `docs/agents/*` 는 EA 소유, `template.html`·`tools/layout_check.js`·`tools/shots.js` 는 DA 소유, `tools/build.py`·`tools/smoke.js` 는 공용(수정 시 EA·DA 합의).
- build 결과물 `dist/HBM_quiz.html` 은 마지막에 build 한 사람의 상태다. 게이트 확인용으로만 쓰고 배포 판단은 W4 에서 EA 가 한다.
- 검사기 규칙이 바뀌면 EA 가 `docs/agents/STANDARDS.md` 에 변경 이력을 남기고 분야 에이전트에 알린다.

## 6. EA Phase 2 (W4) — 기계적 일괄 처리 계획

분야 에이전트 작업이 모두 끝난 뒤(W3 반영 후) EA 가 한 번에 수행한다. 각 단계 뒤 `validate` 전체 실행 + 무작위 50문항 diff 육안 확인.

1. **이관(mv) 적용**: `mv` 가 있는 문항을 대상 파일로 옮기고 대상 파일 `legacy_prefix` 에 원 코드를 추가, `mv` 필드 삭제.
2. **정답 위치 재배치** (분야 × 난이도별 ①–④ 각 25 % ± 3 %):
   - 목표 개수 = ⌊n/4⌋ 또는 ⌈n/4⌉. 과잉 위치의 문항을 결손 위치로 옮긴다.
   - 방식은 **두 보기의 맞바꿈(swap)** 1회 — 정답 보기와 목표 위치 보기만 교환해 나머지 순서를 보존한다.
   - **해설 갱신**: 해설·지문 안의 ①–④ 를 같은 치환으로 바꾸고("②③④는" 같은 묶음 포함), "정답은 ③" 류도 갱신, 이어서 조사(①은/②는…)를 재계산.
   - 제외: 보기 문장에 ①–④ 가 들어 있는 문항, 오름차순 수치 보기 문항(정렬 유지 — 다른 문항으로 균형), `vx: ["POS_FIXED"]` 문항.
   - 검증: `E_EXP_REF_ANSWER` 0 건 유지, `W_EXP_REF_MISMATCH` 증가 없음, 정답 텍스트(보기 문자열) 집합이 문항별로 불변임을 스크립트로 확인.
   - 난수 시드 고정, 변경 전후 매핑을 `docs/reviews/_phase2_positions.json` 에 저장(되돌리기 가능).
3. **`E_JOSA_CIRC` 일괄 수정**: ①③ → 은/이/을/과/으로, ②④ → 는/가/를/와/로.
4. **`[근거] …` 꼬리표 제거**(`I_EXP_SRC_TAG`): 해설 끝의 일괄 부착 출처 문자열 삭제. 분야 에이전트가 `src` 로 옮긴 것만 남는다.
5. **조사 띄어쓰기 정규화**(`I_JOSA_SPACE`): `영문/숫자/단위 + 공백 + 조사(가·는·은·를·을·의·에·와·과·로·으로·에서·에는·에도·까지·부터·보다·처럼·만·도)` 의 공백 제거. 관형사와 구별되지 않는 **'이'** 는 자동 처리하지 않고 목록만 뽑아 수작업 확인.
6. **단위 표기 통일**: μ(U+03BC) → µ(U+00B5), "um" → "µm", "W/mK" → "W/m·K".
7. **최종 확인**: 전체 `validate`(목표: 차단 E 0, W 는 사유 있는 것만), `build`, `smoke`, DA 의 `layout_check` 실행. 분야당 20문항(난이도별 6–7) 무작위 표본 EA 판독 → `docs/reviews/EA_final.md`. 표본 불합격률이 10 % 를 넘는 분야는 해당 에이전트 재작업.

## 7. 완료 판정 (전체)
- 전 분야 게이트 통과 + Phase 2 완료 + 정답 위치 분포 OK.
- NUM·FACT 지적 사항 전부 반영(또는 EA 가 사유 승인).
- EA 표본 판독 불합격률 ≤ 5 % (불합격 = 사실 오류, 정답 비유일, 난이도 부적합, 오답 무의미, 그림·지문 불일치 중 하나라도 해당).
